# AG-12 方案：审计轨迹 / 审批环节 / 模型调用可取消（2026-09-21）

对象：`/home/qing/桌面/bot4cj.cpp` @ HEAD `a78efa8`。
性质：**方案**（本轮不改行为）。目的：把「无审批、无审计、不可取消」这条设计观察拆成可决策的选项。

---

## 0. 先确认现状（逐条实测，不是转述）

| 面 | 现状 | 证据 |
| --- | --- | --- |
| 审计轨迹 | **没有**。唯一的痕迹是 `--verbose` 时的 stderr（`[工具] xxx` + 缩进后的结果）；无时间戳、无持久化、无结构化、默认还可能没开 | `agentloop.cpp` 的 `log()`；`grep -rn 审计轨迹\|audit src/ docs/agent.md` 零命中 |
| 审批环节 | **没有**。`run_command` 与 `run_action_script` 直接执行，没有任何确认 | `agenttools.cpp` 的两个装配函数；docs 只在安全说明第 1 条要求「对外暴露请自己加审批或容器隔离」 |
| 模型调用可取消 | **不能**。`stopRequested()` 只在每轮**开始前**检查一次；调用一旦发出，最长 600 s 阻塞，只能再按一次 Ctrl-C 强杀（而强杀会跳过 `deactivate()`，把执行器留在带电状态） | `agentdriver.cpp:27` 是唯一的检查点；`modules/lib/llm_http.lua` 未设任何进度/中止选项（`grep XFERINFO→零命中`），libcurl 的 `CURLOPT_TIMEOUT` 只兜上限 |

三者性质不同，**建议分开决策**——它们的收益、代价、与部署模型的关系都不一样。

---

## 1. 威胁模型：先分清「给谁用」

缺了这一步，审批会做成一个要么没人用、要么被绕过去的摆设。

| 部署形态 | 谁能影响模型输入 | 已有边界 | 需要的机制 |
| --- | --- | --- | --- |
| **A. 开发/实验**（本项目的主要形态） | 只有操作者自己；模型输出即操作者自己的意图 | 同 UID、无网络暴露 | 审计轨迹够用；审批是负担 |
| **B. 单机生产**（机器人跑在现场，操作者偶尔看） | 摄像头画面、传感器读数、磁盘文件（**都可被环境诱导**） | 无 | 审计轨迹**必要**（事后追责/复盘）；危险动作审批**可选** |
| **C. 远程接入**（`--tcp` 或对外暴露的 agent） | 上述 + 网络对端 | TCP 口令（明文，文档已声明仅限可信内网） | 审计轨迹 + 审批 + 隔离（专用用户/容器）三者都要；**仅靠本项目内置机制不够** |

**关键判断**：C 形态的正确答案仍然是「进程外隔离」，不是「在进程内加一个审批提示」——因为一个能驱动 shell 与硬件的进程，其内置审批层与它保护的目标同权限，绕过去的方式太多（改配置文件、改 `scripts/`、直接调 `run_action_script`）。所以本方案的目标不是「让 C 变安全」，而是：**让 B 可追责（审计），让 A/B 更可控（可取消），并给「想加审批」的人一个不用自己造轮子的入口（策略钩子）。**

---

## 2. 三层方案（按性价比排序）

### P1 —— 审计轨迹（建议无条件做）

**做什么**：新增 `--audit-log <path>`（或配置文件 `audit_log`），以 **JSON Lines** 追加写入每次工具调用：

```json
{"ts":"2026-09-21T17:04:11.238+08:00","turn":2,"tool":"run_command",
 "args":{"command":"ls -l /dev/video0","timeout_seconds":10},
 "ok":true,"exit_code":0,"ms":43,"bytes":{"stdout":812,"stderr":0},
 "session":"<进程启动时生成的短 id>"}
```

**关键设计点**：
- **位置在宿主工具层**（`agenttools.cpp` 的注册表 execute 或 `agentloop.cpp` 的派发点）——这是所有工具调用的唯一漏斗，Lua 驱动与 `.mt` 脚本都绕不过去。放 Lua 侧会漏掉「驱动被直接调用」的路径。
- **图片不进日志**：`capture_image` 的 base64 只记 `bytes` 与 sha256 前缀。否则日志会把每次拍照的数百 KB 灌进磁盘，且可能含隐私画面。
- **`run_command` 的命令原文要记，但密钥要遮蔽**（复用 `agent_subprocess` 已有的敏感名判据 `isSensitiveEnvName`，对 `KEY=...` 形态做遮蔽）。
- **失败也要记**（含超时/中断/预算降级），因为「模型想做什么但没做成」同样是审计信息。
- 默认**关闭**（保持现状语义），开启即 append-only；不引入日志轮转（交给外部工具）。

**代价**：约 200 行（含遮蔽与 JSON 组装）+ 用例。**收益**：B 形态从「无据可查」变成「可复盘」。这也是唯一一条不会与任何部署模型冲突的改动。

### P2 —— 模型调用可取消（建议做，且技术前提已具备）

**做什么**：让模型调用在等待期间能被打断，而不是只能强杀。

**现状约束**：`stopRequested()` 是 C++ 侧的原子标志，而阻塞发生在 Lua 的 libcurl 里——**驱动沙箱拿不到宿主的内存**。所以需要一个跨层的通知通道。两条可行路线：

| 路线 | 机制 | 判别力/代价 |
| --- | --- | --- |
| **P2a 取消哨兵文件** | 第一次 Ctrl-C 时宿主在固定路径（如 `.tmp/agent-cancel`）创建哨兵；`llm_http.lua` 用已有的 `CURLOPT_XFERINFOFUNCTION`（~1 s 回调一次）检查该文件，存在即返回非 0 中止请求，并返回明确的 ERR（"请求已取消"） | 零新依赖（XFERINFO 是 libcurl 自带，只需补两个常量；常量漂移由既有 `test_curl_consts.c` 覆盖）。**缺点**：依赖文件系统作为跨层通道，稍显粗糙 |
| **P2b 宿主注入取消函数** | 宿主把 `stop_requested()` 暴露成驱动可调的全局函数（与 `driver->playQuiet` 同一注入机制） | 更干净、无文件副作用。**缺点**：扩大了驱动可见的宿主 API 面，需要想清楚权限边界（驱动本来就能驱动硬件，所以增量能力有限） |

**建议 P2a 先行**（改动最小、不动沙箱可见面），P2b 作为后续整理。两者都必须配 libcurl 的进度回调才能真正「及时」中止——只设 `CURLOPT_TIMEOUT` 是做不到的。

**同时必须处理的语义**：中止后 `runTurn` 的回滚边界（`complete`）如何推进、会话是否可继续。建议与 AG-1 同一口径：中止发生在「半截 tool_calls 序列」之前时回滚本轮，REPL 可继续下一条任务；并在回执里如实说明「本次模型调用被取消」。

### P3 —— 审批（**不建议做成内置交互式**；建议提供策略钩子）

**为什么不做交互式确认**：agent 模式的价值是「多轮自主推进」，一次任务里可能有十几次工具调用；逐个问会让人放弃使用或直接加 `--yes`（等于没有）。而且危险面主要是 `run_command`，它本身已有开关（`--agent-shell`，缺省关闭，配置文件不能开）——**已经是一个粗粒度的人为闸门**。

**建议做法**：承认「审批是部署策略」，只提供一个**声明式策略钩子**，把判断权交给使用者：

```
--agent-policy <path>        # 可选；缺省不设 = 现状（全部放行）
```

策略文件（严格 JSON，与 llm 配置同解析器）声明**哪些工具在什么条件下需要确认**：

```json
{ "require_confirm": ["run_command"],
  "confirm_command": "/usr/local/bin/notify-and-approve",   // 外部程序：读 stdin 的 JSON，退出 0 = 放行
  "confirm_timeout_sec": 30,
  "on_timeout": "deny" }
```

- 需要确认时，宿主把工具名与参数（同样遮蔽后的形态）交给外部程序，按其退出码放行/拒绝；超时按 `on_timeout` 处理（建议默认 **deny**，与全仓 fail-closed 一致）。
- **为什么交给外部程序**：审批的形态（终端 y/n、手机推送、工单系统）随部署而变，本项目不该猜；而外部程序天然可以做到「人在环」，且不扩大沙箱可见面。
- 默认**不启用** ⇒ 零行为变更；启用者显式承担「确认程序必须可靠」的责任。

**代价**：中等（策略解析 + 调用外部程序 + 超时/拒绝路径 + 用例）。**收益**：给 B/C 形态一个不用自己造轮子的入口，同时不假装「内置审批 = 安全」。

## 3. 建议的落地顺序与决策点

| 顺序 | 动作 | 依赖 | 建议 |
| --- | --- | --- | --- |
| 1 | **P1 审计轨迹** | 无 | **做**（唯一无争议项；也是 P3 的前提——先有记录，再谈审批） |
| 2 | **P2a 模型调用可取消** | 无 | **做**（把「按两次 Ctrl-C 强杀、跳过清理链」这个真实缺陷消掉） |
| 3 | P3 策略钩子 | P1 的遮蔽/序列化逻辑可复用 | 看部署需求；默认关闭 |
| 4 | P2b 替代 P2a | — | 仅在觉得「哨兵文件」不可接受时 |

**需要你决策的三点**：
1. **P1 的位置**：审计日志落**文件**（`--audit-log`）还是 **stderr**（可被 systemd/journald 收走）？前者自带轮转问题，后者依赖外部收集。建议：两者都支持（`--audit-log -` 表示 stderr）。
2. **P2 的通道**：接受「哨兵文件」这种跨层方式吗？若不接受，就上 P2b（暴露宿主函数给驱动）。
3. **P3 要不要现在做**：如果不打算支持远程接入（C 形态），P3 可以只留在文档里。

---

## 4. 明确不做的事

- **不做内置交互式逐次确认**（理由见 P3）：会破坏 agent 的核心用法，且容易被 `--yes` 架空。
- **不把审批层当作 C 形态的安全边界**：进程内审批与它保护的目标同权限；C 形态仍需专用用户/容器/网络命名空间（文档已如此声明，本方案不改这条口径）。
- **不记录图片内容**：审计日志记字节数与摘要，不记 base64（体积 + 隐私）。
- **不做「模型调用中途可恢复」**：取消就是取消，不做续传（复杂度与收益不成比例）。
