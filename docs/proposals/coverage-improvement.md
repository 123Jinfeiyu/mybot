# AG-11 覆盖率门禁：口径分析与方案（2026-09-21）

对象：`/home/qing/桌面/bot4cj.cpp` @ HEAD `a78efa8`。
性质：**方案**（本轮不改门禁行为）。所有数字为本机实测。

## 0. 结论先行

**不要加行覆盖阈值。** 实测发现当前这个数字既**偏低**（漏测了 `mybot` 二进制的全部端到端路径）又**有结构性盲区**（fork/exec 子侧代码恒为 0%），两个方向的偏差同时存在时，一个阈值既挡不住倒退、又会奖励盲区。建议改为三件事：修测量口径 + 把真机链路纳入测量 + 用**行为断言**替代那部分测不到的代码。

## 1. 实测基线

| 项 | 实测值 |
| --- | --- |

**"叠加全套守门后覆盖完全不变"是这次分析最关键的一条发现。** 原因：`mybot` 二进制**没有**插桩——`run_coverage.sh` 只把 `--coverage` 加进 C++ 编译标志并只构建 `mybot_tests`（`cmake --build "$build_dir" --target mybot_tests`），于是 `run_all.sh` 里跑的 e2e 用的 `./build-cov/mybot` 不带任何计数器。也就是说：

> 当前数字 = 「仅 C++ 单测」覆盖 `src/`。而 `main.cpp` 的流水线、agent 的一次性任务与 REPL 外壳、TCP 动作源、管道模式——**项目里体量最大的几条真实链路一个字符都没被计入**。

顺带一个静默失真：脚本不清理陈旧 `.gcda`，实测报

```
libgcov profiling error: .../test_llmconfig.cpp.gcda: overwriting an existing
profile data with a different checksum
```

即重建二进制后不删旧计数文件，gcov 会报错并**混合两套构建的数据**——数字来源不明。

## 2. fork/exec 盲区：实测确认

`src/agent_subprocess.cpp` 的 `--requires` 区块在报告里**恒为 0%**：

```
function ...revokeInheritedFds()   called 0 returned 0% blocks executed 0%
function ...execShellChild(...)    called 0 returned 0% blocks executed 0%
```

而同文件的测试是**通过**的。原因不是「没测」，而是插桩模型与进程模型不相容：gcov 的计数器在 `atexit` / `__gcov_exit` 时落盘，而这两个函数**永远以 `execve` 结束**——exec 会用新映像的计数器覆盖当前进程的全部计数页，子侧那段代码的执行记录不可能被写出。

这正是审计报告里点出的那句「**容易给人『子进程安全代码已被覆盖』的错觉**」。而且它不是无关紧要的一块：AG-3（`close_range` 标志写错、快速路径从未执行）**正好藏在这里**，而且藏了很久——因为该区块对所有读者显示 0%，所有人都默认「那是有意不测的部分」。

## 3. 为什么「加阈值」是错的解法

1. **阈值会奖励盲区**：`revokeInheritedFds` 那 20 行无论怎么改都是 0%，把阈值定到 85% 只会逼人在**测得到的区域**堆测试，测不到的区域反而更没人看——缺陷正好往那里躲。
2. **分母本身可疑**：当前分母只含单测触达的行，`main.cpp` 的链路完全不在分子里；在这个数字上设阈值等于给一个定义不完整的指标设 KPI。
3. **已有先例说明阈值不是这里的瓶颈**：项目自己已经选择了「未设 `COV_MIN_LINES` 时只报告」，changelog 也写明「起步阶段用拍脑袋的数字卡住 CI 只会逼人调低阈值」。这个判断是对的，缺的是**把数字做可信**。

## 4. 建议方案（三件，按性价比排序）

### P1 —— 测量口径修正（小改动，立即消除假数据）

`test/run_coverage.sh` 三处：

1. **采集前清 `.gcda`**：消除 `different checksum` 混算，保证数字来自当次构建。
2. **让 `mybot` 也被插桩**：构建 target 加上 `mybot`（`--coverage` 已在 `CMAKE_CXX_FLAGS` 里，链接标志也已给），这样 `run_all.sh` 的 e2e 才真的进分子。
3. **增加一个可选的「全链路」模式**：`COV_WITH_GATE=1` 时在采集前后各跑一次 `ALLOW_SKIP=1 bash test/run_all.sh`，让 e2e 的贡献可见；缺省仍是「只单测」的快路径（保持 CI 时长可控）。

收益：数字第一次如实反映「单测 vs 全链路」的差距；e2e 覆盖的 `main.cpp` / agent 流水线首次进入统计。代价：全链路模式慢（约 2 分钟），故做成可选。

### P2 —— fork/exec 区块改用**行为断言**（本项真正的收口）

不再试图测量它，而是**直接断言它的行为**。两条路线，建议都要（都不依赖覆盖率工具）：

**P2a 子进程自报（轻，推荐先做）**
`execShellChild` 在 fork 之后、exec 之前，把「走了哪条路径」写进一个由父进程传入的 fd 或用 `write(2)` 写一个路径固定的标记文件（fork 后可用栈上缓冲，`snprintf` + `write` 不分配堆内存，符合该函数现有的「不 malloc」约束）。测试断言标记内容 + 目标行为（fd 已吊销、进程组已终止）。
这条**本来就能抓住 AG-3**：只要断言「标记必须是 `close_range` 路径」，标志写错时标记会变成 `fallback`。

**P2b `LD_PRELOAD` 拦截 `syscall()`（重，判别力最强）**
用一个小的 `*.so` 拦截 `syscall()`：既能把实际 flags 记下来，也能强制返回 `EINVAL` 以驱动退化路径，从而**分别**验证两条路径都真的有效。审计方复现 AG-3 用的就是这个装置，已验证可行（真实子进程里观察到 `close_range(...,flags=1)==-1 errno=22`）。代价：增加一个编译产物与一段 `run_all.sh` 装置段落，且依赖 glibc 的 `syscall()` 可被 interpose（本机实测可）。

**注意 P2a 与 P2b 的分工**：P2a 证明「代码选了哪条路」，P2b 证明「两条路都真的吊销了 fd」。前者便宜且能防 AG-3 复发，后者贵但覆盖「退化路径本身是否正确」——后者目前由既有的两条防泄漏用例间接保证（它们只断言 CLEAN/LEAKED，对分支不敏感）。

### P3 —— 文档与过滤器修正（顺手，避免继续误导）

1. `docs/agent.md:415` 推荐的 `./build/mybot_tests agent` 只命中 **86/436** 例：它是**子串**匹配，漏掉 `promptpack`（11 例）、`llmconfig`、`cliargs` 等同样属于 agent 配置面的用例——而注释里恰恰写着「proto / driver / tools / loop / config」。要么把过滤器改成按**作用域**匹配（我给用例名加前缀或提供 `--scope agent`），要么把文档改成如实描述它命中什么。
2. `docs/testing.md` 的覆盖率小节写明：当前数字只含单测、`mybot` 未插桩、fork/exec 区块恒 0% 且**不是「没测」而是「测了但测不到」**——把这条写进文档，读者才不会再次误判。

## 5. 不建议做的事

- **不要**设 `COV_MIN_LINES` 硬阈值（理由见 §3）。
- **不要**为了让 `agent_subprocess.cpp` 的数字好看而把 `close_range` 调用抽到父进程或加「可测试」间接层——那是为指标改结构，且会让真正的安全语义变形。
- **不要**在 fork 子进程里调 `__gcov_dump()`：exec 会覆盖计数页（见 §2），而且在 fork 后调用 libgcov 属于「子进程里跑带锁的库代码」，与该函数刻意「不分配堆内存」的约束冲突。

## 6. 建议的落地顺序

| 顺序 | 动作 | 工作量 | 收益 |
| --- | --- | --- | --- |
| 1 | P1 测量口径修正（清 gcda + 插桩 mybot + 可选全链路模式） | 小 | 数字可信，不再报假数据 |
| 2 | P3 文档与过滤器修正 | 小 | 停止误导（含把盲区写清楚） |
| 3 | P2a 子进程路径自报 + 断言 | 中 | **让 AG-3 那类缺陷不可能再静默复发** |
| 4 | P2b LD_PRELOAD 双路径验证（可选强化） | 中 | 退化路径本身也有独立证据 |

第 3 项是这一批真正的价值所在；1、2 是让它不误导人的前提。
